# Watch Anything MVP 需求文档

**版本：** v1.0  
**状态：** 已确认，待实施计划  
**目标：** 在剩余约 12 个有效工作小时内完成一个可以部署、可以演示真实闭环的 SaaS MVP。  
**预算：** 额外现金支出不超过 50 元人民币。  
**关联设计：** [MVP 技术与架构设计](./2026-08-04-watch-anything-mvp-design.md)

## 1. 产品定义

Watch Anything 让用户用一句自然语言描述“想持续关注什么”。系统把模糊描述整理成可检查的 Radar 规则，定期搜索公开信息，筛选重要的新结果，并通过 Telegram 通知用户。

本项目的重点不是覆盖所有社交媒体，而是证明下面这条真实链路可以工作：

> 用户输入需求 → AI 生成规则 → 用户确认 → 登录/注册 → 绑定 Telegram → 创建 Radar → 定期获取公开信息 → AI 筛选 → Telegram 通知

### 1.1 目标用户

需要持续关注某个主题、但不想每天手动查看多个网站的人。例如：

- 关注 LISA 的官方发布、巡演和合作消息。
- 关注 OpenAI 的模型、API 和官方公告。
- 关注香港教师招聘信息。

### 1.2 MVP 成功标准

测试者能够在真实部署地址完成以下操作：

1. 不登录直接输入一条关注需求。
2. 看到 AI 正在整理需求，并进入规则确认页。
3. 检查并确认规则。
4. 登录或注册，且刚才确认的规则不会丢失。
5. 连接同一个 Telegram Bot。
6. 创建第一个 Radar，并完成一次首次基线检查。
7. 看到 Dashboard、Radar 详情和运行记录。
8. 创建第二个 Radar 时不重复登录和绑定 Telegram。
9. 至少收到一条带 Radar 名称、来源链接的真实 Telegram 通知。

## 2. 范围边界

### 2.1 必须完成（P0）

- Landing 页面访客输入需求。
- 首页显示短暂的 AI 整理状态。
- 规则确认页展示并允许最小范围编辑：Radar 名称、关注项、忽略项。
- 独立 Auth 页面：登录为主入口，注册为次入口。
- Auth 成功后恢复刚才确认的规则。
- 独立 Telegram 连接页，使用一个账号级共享 Bot。
- Telegram 未连接时不能创建 Radar。
- 每个用户最多 3 个运行中的 Radar；暂停的 Radar 不占用名额。
- 至少接入一种公开搜索来源和一种固定的 RSS 来源。
- 运行时进行去重、规则匹配和重要度判断。
- Dashboard 显示 Radar 状态、Telegram 状态和最新重要发现。
- 独立 My Radars 页面展示和管理完整 Radar 列表。
- Radar 详情显示规则、最近发现和运行记录。
- 真实 Telegram 通知。
- 英文和简体中文核心网页 UI。
- 部署到可访问的真实 URL，并能上传 GitHub。

### 2.2 明确不做

- Instagram、X、微信等封闭平台的官方直连。
- 任意用户提交 URL 后由服务器抓取。
- 任意 RSS 管理后台。
- 复杂 Telegram 对话式管理。Bot 只负责绑定、帮助和发送通知。
- 计费、团队、权限协作、导出、复杂分析报表。
- 多 Bot。所有 Radar 共用同一个账号级 Telegram Bot。
- 自动暂停用户已有 Radar。
- 独立 Activity 页面、All Findings 页面和 KPI 数据大屏。
- 为了赶进度而用假数据替代部署后的核心闭环。

### 2.3 可延后（P1/P2）

- 更多 RSS 来源选择。
- 更丰富的模板。
- Telegram 通知的完整中文本地化。
- 更复杂的失败重试、统计和运营后台。
- 自定义域名、付费套餐和商业化能力。

## 3. 用户流程和页面要求

所有创建流程页面都是独立页面，不使用弹窗承载主流程。页面可以共享导航和语言选择，但不能要求用户重复填写已经提交的需求。

### FR-01 Landing 输入

**页面：** `/`  
**用户动作：** 输入需求并点击“创建 Radar”。  
**系统行为：** 保留当前输入，显示 AI 整理状态，然后进入规则页。未登录不能阻止用户先查看规则。

**验收标准：**

- 输入框在首屏清晰可见。
- 点击后按钮进入 loading/disabled 状态。
- 需求文本在下一页可见。
- AI 失败时保留原始文本，并提供重试入口。

### FR-02 规则确认

**页面：** `/rules`  
**展示内容：** 原始需求、Radar 名称、关注项、忽略项、生成的搜索词、重要度阈值、固定检查频率。

**用户可以修改：**

- Radar 名称。
- 关注项和忽略项的增删。

**用户不能直接控制：**

- Provider 名称。
- 任意 URL 抓取目标。
- 后台定时任务实现细节。

**验收标准：**

- 用户可以明确看懂“AI 将关注什么”和“AI 将忽略什么”。
- 点击确认后保存已确认的规则，未登录时进入 Auth。
- 返回首页不会丢失输入。

### FR-03 Auth

**页面：** `/auth`  
**默认状态：** 登录。  
**次要入口：** 注册。  
**字段：** 邮箱、密码、忘记密码入口或明确的 MVP 占位状态。

**验收标准：**

- 登录和注册共用一套页面，不创建两套不同的认证体验。
- 登录或注册失败时显示靠近表单的可读错误。
- 成功后恢复刚才确认的规则；尚未绑定 Telegram 时进入连接页，已经绑定时直接创建 Radar 并进入详情页，不要求重复绑定。
- 刷新、浏览器返回或 Telegram 回跳后仍能恢复当前创建流程；过期时给出明确重新开始入口。
- 从首页右上角登录成功后直接进入 Dashboard，不进入创建流程。
- 回跳地址只能是站内允许的路径。

### FR-04 Telegram 连接

**页面：** `/connect-telegram`  
**连接模型：** 一个用户账号绑定一个 Telegram 私聊；该连接服务于该账号下所有 Radar。

**页面步骤：**

1. 打开真实的 Telegram Bot 链接。
2. 用户在私聊中点击 Start。
3. 返回网站确认连接。

**验收标准：**

- 未连接、等待、已连接、失败四种状态可区分。
- Bot 连接成功前，“创建 Radar”不可用。
- 连接完成后，创建第二个 Radar 不重复绑定。
- Bot 不承担 Radar 创建、编辑、暂停等网站管理功能。

### FR-05 创建 Radar 和多 Radar

**创建条件：** 用户已登录、规则已确认、Telegram 已连接。

**Radar 生命周期状态：** 运行中、已暂停。首次基线及后续检查的**运行记录状态**另行使用运行中、成功、失败三种状态。

**限制：** 每个用户最多 3 个运行中的 Radar；暂停的 Radar 不占用运行名额。达到上限时，用户必须主动暂停一个 Radar，系统不能自动暂停。

**验收标准：**

- 创建成功后进入新 Radar 的详情页，看到首次检查正在运行；可通过 My Radars 返回完整列表。
- 第一个 Radar 的数据不会覆盖第二个 Radar。
- 第二次和第三次创建可以复用已有登录和 Telegram 状态。
- 创建后自动开始首次基线，旧信息不触发通知。

### FR-06 信息获取和处理

**MVP 来源：**

- 一种公开搜索 API。
- 一个服务器配置的固定 RSS 来源。

不承诺完整整合 Instagram、X、微信等平台。用户只看到来源域名、标题、发布时间和原文链接，不看到 Tavily、RSS、HTTP 状态码等实现细节。

**处理步骤：**

1. 按规则获取公开候选信息。
2. 标准化标题、来源和链接。
3. 按 canonical URL 或标题+域名指纹去重。
4. 排除旧闻、重复报道和规则明确忽略的内容。
5. 由 AI 判断相关性、可信度和重要度。
6. 保存结果和判断理由。

**验收标准：**

- 同一个事件不会重复通知。
- 规则匹配失败的内容可以保存为未通知结果。
- 两个来源中至少一个成功时保留结果，整体运行状态显示为“成功”；另一个来源的错误只记录在内部日志。
- 所有来源都失败时显示运行失败和重试入口。
- 至少一个来源成功后，AI 判断、语义去重或 Telegram 通知失败不能再把 Run 改成失败；这些问题记录为内部处理或通知状态。

### FR-07 Dashboard

**页面：** `/dashboard`  
**必须呈现：**

- Telegram 连接状态。
- Radar 总体状态，例如运行中、暂停和需要处理的数量。
- 跨 Radar 的最新 3 条重要发现。
- 需要用户处理的问题，例如连续运行失败或 Telegram 未连接。
- 新建 Radar 和查看全部 Radar 的入口。

**不需要：** KPI 统计卡、独立 Activity 页、复杂筛选报表。

**验收标准：**

- 用户能一眼判断系统是否正常以及最近发现了什么。
- 点击“查看全部 Radar”进入 `/radars`。
- 没有发现时显示明确空状态。

### FR-08 My Radars、Radar 详情和运行记录

**列表页面：** `/radars`

My Radars 必须呈现完整 Radar 列表。每项显示名称、运行中/已暂停、最近检查、下次检查和新发现数量，并提供新建入口。用户在这里管理多个 Radar；Dashboard 不重复完整列表。

**详情页面：** `/radars/:id`  
**必须呈现：**

- Radar 当前状态和下次检查时间。
- 当前规则。
- 最新发现。
- 运行记录入口。
- 暂停/恢复、立即检查、编辑规则入口。

**运行记录至少记录：** 检查开始/结束、来源数量、候选数量、相关数量、通知数量、运行状态和用户可读错误说明。

**用户可见的运行状态只有三种：** 运行中、成功、失败。Provider 具体名称和内部错误只写日志，不进入产品文案。

### FR-09 Telegram 通知

每条通知必须包含：

- Radar 名称。
- 重要发现标题和简短摘要。
- 来源域名或原文链接。
- 重要度/匹配度的简短说明。

同一个 finding、同一个渠道和同一个目的地不能重复发送。

MVP 采用 at-most-once：Notification 在调用 Telegram 前必须被原子领取；发送结果不确定时不自动重发。验收优先保证不会因任务重试连续发送相同提醒，接受极端网络异常下可能漏掉一次通知。

### FR-10 多语言和响应式

- 核心网页支持 English 和简体中文。
- 语言切换覆盖 Landing、Rules、Auth、Telegram、Dashboard、详情、运行记录、表单和错误。
- 用户输入、品牌名、Radar 名称、LISA、OpenAI、Telegram 等专有名词不强制翻译。
- 390 × 844 无横向滚动，核心按钮不会消失。
- 移动端可以使用紧凑导航或底部导航，但必须保留 Dashboard、Radars、Telegram 的核心入口。

## 4. 外部依赖和实现约束

需求文档只规定用户可观察的结果，具体技术选型由后续技术设计确认。当前约束如下：

- 使用免费或低成本额度，自动付费和不受控超额关闭。
- API Key、Bot Token、数据库服务密钥只能在服务端使用。
- Telegram 上线必须真实注册 HTTPS Webhook、配置 secret_token，并完成一次 `/start` 回调验证；只有 Bot Token 不算完成绑定能力。
- 开发环境可以使用固定 fixture/mock 验证流程，但部署演示必须完成一次真实搜索和一次真实 Telegram 通知。
- 首版可以使用 Vercel 的免费 `vercel.app` 地址，不要求先购买域名。
- 部署不能只停留在本地服务。
- 所有影响用户流程的第三方失败都必须映射到明确的用户状态（运行中、成功或失败），不允许静默卡住；来源级错误可以留在内部日志。

## 5. 最小数据对象

这里只定义业务对象，不提前锁死表结构：

- **User：** 登录身份、语言、Telegram 连接状态。
- **Radar：** 用户、名称、原始需求、规则、状态、检查频率、下一次检查。
- **Run：** Radar、开始/结束时间、状态、候选/相关/通知数量、错误说明。
- **Finding：** Radar、标题、摘要、来源域名、原文链接、匹配度、是否重复、是否已通知。
- **Notification：** finding、Telegram 目的地、发送状态、发送时间。

## 6. 安全、隐私和可靠性最低要求

- 用户只能看到自己的 Radar、Run、Finding 和 Notification。
- Bot 绑定使用一次性 token，不能重复使用。
- Telegram chat_id、API Key、密码等敏感信息不能进入前端代码或公开日志。
- 运行和通知必须具备基本幂等性，重复触发不会产生重复 Radar 或重复通知。
- 登录前 AI 生成的不可编辑规则必须由服务端签名或持久化；登录后只接受允许编辑字段，不能依赖 disabled 输入框防篡改。
- 当前创建流程的 setup 只能恢复给所属用户，且必须具备过期和消费状态。
- 搜索来源必须来自服务端 allowlist，客户端不能提交任意 URL 让服务器抓取。
- 两个来源中只要有一个成功，运行就显示成功并保留可用结果；只有全部来源失败时才显示失败。

## 9. 原型与生产 MVP 的已知差距

当前 HTML 原型主要验证页面结构、文案和点击路径，不代表接口已经实现。后续开发必须把下面这些差距当作待实现事项，而不是重新设计页面：

| 原型现状 | 生产 MVP 要求 |
|---|---|
| 规则字段主要是展示文本 | Radar 名称、关注项和忽略项可以最小范围编辑并保存 |
| Telegram 按钮模拟等待状态 | 使用真实 Bot 链接和一次性绑定状态 |
| Dashboard 和 My Radars 使用固定示例数据 | Dashboard 读取真实跨 Radar 概览，My Radars 读取完整真实列表；多个 Radar 互不覆盖 |
| 运行记录使用示例数据 | 由真实运行写入运行中、成功或失败状态 |
| 首页有旧流程遗留 markup | 独立页面路由是生产流程唯一来源，旧 markup 不得被打开 |

这些差距不否定原型。原型回答“页面如何工作”，生产实现再补上认证、数据库、搜索、AI、调度和 Telegram 接口。

## 10. 已由技术设计解决的选择

以下问题已经锁定，不在实施时临时更换：

1. 搜索使用 Tavily Basic，AI 使用 Groq `openai/gpt-oss-20b`。
2. 登录使用 Supabase Auth。
3. 定时任务使用 Supabase Cron。
4. RSS 使用服务器固定的 Music-News.com feed。
5. UI 使用 shadcn/ui + Tailwind + Lucide，表单使用 React Hook Form + Zod。

具体额度、安全和失败策略以关联技术设计为准。
