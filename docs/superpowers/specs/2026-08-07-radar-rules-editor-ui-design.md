# Radar Rules Editor UI Design

**Status:** Approved direction

**Date:** 2026-08-07

## Goal

让 Radar 详情页的规则编辑行为和规则信息保持同一上下文。用户点击“编辑规则”后，应在“监控规则”卡片内完成查看、修改、保存或取消，不再把表单插入顶部操作区并推动整页内容下移。

## Current issue

当前 `RadarActions` 同时承载暂停、立即检查和编辑操作。编辑表单挂在顶部操作按钮下方，规则摘要仍显示在右侧卡片中，导致：

- 编辑内容和被编辑的规则摘要分离；
- 桌面端保存区域不在规则卡片内，信息层级不一致；
- 移动端表单展开后会把发现列表整体推远；
- 原型中的规则卡片“Edit”入口没有被复用。

## Design decision

推荐采用“规则卡片原地编辑”方案：

1. 顶部仍保留暂停/恢复和立即检查，移除顶部的独立“编辑规则”按钮。
2. 规则卡片标题行右侧增加 `编辑` / `Edit` 文字按钮。
3. 未编辑时继续显示关注内容、忽略项、监控主题、频率、下次检查和阈值等真实摘要。
4. 编辑时，规则卡片切换为表单态，包含：
   - Radar 名称；
   - 关注项，每行一项；
   - 排除项，每行一项；
   - 保存和取消按钮。
5. 保存继续调用现有 `PATCH /api/radars/[id]` 的 `update_rules` action。成功后刷新服务端数据并回到摘要态；失败时在卡片内保留用户输入并显示错误。
6. 取消时丢弃未保存输入并回到摘要态。再次打开编辑时使用最近一次服务端数据初始化。

## Responsive behavior

- 桌面端规则卡片保持在右侧 sticky 区域，编辑表单在卡片内部展开，不改变主发现列表的结构。
- 移动端规则卡片继续排在发现列表之后，表单使用单列布局，控件高度保持至少 40px，操作按钮允许换行。
- 编辑态不新增模态框或抽屉，避免遮挡发现内容和引入额外交互层。

## Data flow and error handling

- `RadarDetailPage` 继续提供真实的 `radarName`、`includeTopics` 和 `excludeTopics`。
- `RadarActions` 保留请求、校验、忙碌态和错误处理逻辑，但只负责顶部业务按钮及向规则编辑器传递状态。
- 规则编辑器可以作为同文件内的独立展示单元，避免改变 API 或数据库模型。
- 保存前校验 Radar 名称 2–80 个字符；关注项 1–8 项、每项 1–60 个字符；排除项最多 8 项、每项 1–60 个字符。
- 保存期间禁用编辑表单操作；取消按钮在请求期间禁用，避免丢失仍在提交的数据。
- API 错误、网络错误和校验错误都在规则卡片内展示，顶部全局错误提示继续用于暂停/恢复/立即检查。

## Testing

补充或调整组件测试，覆盖：

- 默认显示规则摘要和卡片内编辑入口；
- 点击卡片编辑后显示当前 Radar 名称、关注项、排除项；
- 校验失败时保留表单并显示对应字段错误；
- 保存成功发送现有 PATCH payload，刷新并退出编辑态；
- 保存失败保留编辑态和输入；
- 取消不发送请求并恢复摘要态；
- 英文和简体中文的编辑入口、按钮和错误文案；
- 桌面/移动布局使用现有响应式 class，不引入新的依赖。

## Out of scope

- 不改变规则解析、创建 Radar、Supabase 认证和 API contract；
- 不增加编辑搜索查询、重要性阈值或检查频率的后端更新能力；
- 不新增弹窗、抽屉、撤销历史或批量编辑。
