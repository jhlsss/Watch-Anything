# Watch Anything MVP 需求文档审核

**审核对象：** `docs/superpowers/specs/2026-08-05-watch-anything-mvp-requirements.md`  
**审核结论：** DONE_WITH_CONCERNS。可以作为后续技术设计和实施计划的输入，但需要用户确认范围冻结。  
**审核方式：** 对照当前原型、已确认产品决策、MVP 设计文档和剩余约 12 小时的交付约束进行检查。

## 1. 覆盖性

**通过。** 文档覆盖了完整用户链路：

`Landing → Rules → Auth → Telegram → Create Radar → Dashboard → Detail/Run history → Telegram notification`

也覆盖了本次项目最重要的产品约束：

- 多 Radar，最多 3 个运行中。
- 一个账号共用一个 Telegram Bot 连接。
- 登录/注册后恢复刚才确认的规则。
- 搜索 API + 固定 RSS，不承诺 Instagram/X/微信直连。
- Provider 技术名称不展示给最终用户。
- 英文/简体中文和 390 × 844 移动端。
- 部署到真实 URL，而不是只运行在本地。

## 2. 一致性检查

### 与原型一致的部分

- 主流程使用独立页面，不依赖弹窗。
- Landing 保留输入需求和 Telegram 手机预览。
- Rules、Auth、Telegram、Dashboard、Radar 详情和运行记录都有对应页面。
- Dashboard 以多 Radar 管理和最新发现为核心，没有重新加入 KPI 大屏或 Activity 页面。
- Telegram 是账号级连接，不是每个 Radar 创建一个 Bot。

### 明确记录为“后续实现差距”的部分

- 原型规则字段还不能编辑。
- 原型 Telegram 连接仍是模拟等待。
- 原型 Dashboard 有固定 demo 数据。
- 原型运行记录有示例状态。

这些不是需求文档错误，反而应该明确写出来，避免后续实现窗口误以为原型已经接通接口。

## 3. 可执行性检查

**通过，但时间风险极高。** P0 只保留了能证明闭环的能力：真实认证、真实 Telegram、至少一个搜索来源、规则筛选、去重、通知、多个 Radar 和部署。没有把支付、团队、复杂爬虫、任意 URL 抓取和分析系统塞进 MVP。

剩余 12 小时更紧张，因此实施计划必须采用纵向切片：每一片都从页面到数据库、API 和外部服务走通，不要先做完整前端再最后接接口。若某个外部集成卡住，应优先保住一条可部署的真实闭环，再推迟非核心来源和视觉润色。

## 4. 发现并处理的风险

| 风险 | 处理结果 |
|---|---|
| 用户说一句话后无法生成可执行规则 | 要求结构化规则，并允许最小编辑 |
| Auth 或 Telegram 中断后已确认规则丢失 | 要求保存已确认规则并恢复 |
| 多 Radar 互相覆盖 | 要求 Radar 持久化、独立详情和 3 个运行中上限 |
| 搜索来源失败导致整个运行消失 | 至少一个来源成功即整体成功并保留可用结果；全部失败才显示失败 |
| 用户看到 Tavily/RSS 等内部实现 | 明确禁止 provider 名称进入产品文案 |
| 只做本地演示，无法证明 SaaS | 明确要求真实部署 URL 和一次真实 Telegram 通知 |
| 运行状态过多让用户困惑 | 用户可见状态固定为运行中、成功、失败；来源错误留在内部日志 |
| 12 小时被非核心功能耗尽 | 明确 P0、P1/P2 和不做清单 |

## 5. 仍需在技术设计阶段做出的决定

这些不阻塞需求文档，但必须在写计划时一次性确定：

1. 认证采用 Supabase Auth 还是自建邮箱密码认证。按 12 小时约束，Supabase Auth 是默认推荐方案。
2. 搜索 API 和模型提供商的具体免费额度与每日限制。
3. 定时任务使用 Supabase Cron、Vercel Cron 还是其他免费方案。
4. 首个固定 RSS 来源和部署环境变量清单。

## 6. 审核结论

需求文档可以作为下一步技术设计和实施计划的唯一产品基线。当前不需要继续修改原型，也不应该在写计划前增加新页面或新模块。由于只剩约 12 小时，下一步计划必须按“先部署探针、再完成一条真实闭环、最后扩展多 Radar 和润色”的顺序执行。

下一步应先得到用户对需求范围的确认，再编写技术设计和按小时拆分的实施计划。
